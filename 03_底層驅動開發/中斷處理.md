## 📌 Context: 為什麼需要中斷？

**中斷 (Interrupt)** 是讓硬體「打斷」CPU 當前工作的機制。

-   **沒有中斷 (Polling)**: CPU 必須不斷詢問「資料來了嗎？」，浪費算力且反應慢。
-   **有中斷**: CPU 專心做別的事，資料來了硬體主動通知 CPU。

**類比：**
你正在寫程式 (Main Task)。
-   **Polling**: 每隔 10 秒你看一眼手機有沒有訊息。 (效率低)
-   **Interrupt**: 你專心寫code，手機響了 (IRQ)，你接起來看 (ISR)，看完繼續寫。 (效率高)

## 🧠 Mental Model (核心觀念圖解)

### 1. 中斷生命週期 (Interrupt Lifecycle)

```text
┌─────────────┐       ┌─────────────┐       ┌─────────────┐
│  Hardware   │──────→│     GIC     │──────→│     CPU     │
│ (HW Signal) │       │ (Controller)│       │ (Exception) │
└─────────────┘       └─────────────┘       └──────┬──────┘
                                                   │
                                            ┌──────↓──────┐
                                            │ Kernel ISR  │
                                            │ (Top-half)  │
                                            └──────┬──────┘
                                                   │
                                            ┌──────↓──────┐
                                            │ Bottom-half │
                                            │ (Thread/WQ) │
                                            └─────────────┘
```

### 2. Top-half vs Bottom-half

Linux 將中斷處理分為兩半，以解決「既要快，又要處理大量資料」的矛盾。

```text
       中斷發生！
          │
          ▼
┌───────────────────┐
│   Top-half (硬)   │ ⚡ 必須快！不能睡眠！
│ ----------------- │
│ • 關閉本地中斷     │
│ • 確認硬體狀態     │
│ • 排程 Bottom-half│
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Bottom-half (軟)  │ 🕒 可以慢，可以睡眠 (部分機制)
│ ----------------- │
│ • 讀取大量資料     │
│ • 複雜運算         │
│ • 呼叫睡眠函數     │
└───────────────────┘
```

## 🔷 Logic I: Linux Kernel 軟體機制

### 1. 驅動開發：如何撰寫中斷處理程式？

現代 Linux Driver 強烈建議使用 **Threaded IRQ**。

#### 核心 API (Threaded IRQ)

```c
/* 申請 Threaded IRQ (最現代的寫法) */
int devm_request_threaded_irq(struct device *dev,
                              unsigned int irq,
                              irq_handler_t handler,      /* Top-half (可為 NULL) */
                              irq_handler_t thread_fn,    /* Bottom-half (Thread) */
                              unsigned long irqflags,
                              const char *devname,
                              void *dev_id);

/* 優點：
 * 1. Bottom-half 自動在 Kernel Thread 執行，可以睡眠 (Mutex OK)。
 * 2. 如果 Top-half 很簡單，甚至可以設為 NULL，全交給 Thread。
 * 3. 實時系統 (RT) 友好。
 */
```

#### 完整範例 (Recommended Pattern)

```c
/* Bottom-half: 在線程中執行，可以睡眠 */
static irqreturn_t my_thread_fn(int irq, void *dev_id)
{
    struct my_device *priv = dev_id;
    
    /* 因為可以睡眠，所以可以用 Mutex 鎖 */
    mutex_lock(&priv->bus_lock);
    
    /* 處理耗時任務，例如讀取 I2C/SPI 資料 */
    i2c_smbus_read_byte_data(priv->client, REG_DATA);
    
    mutex_unlock(&priv->bus_lock);
    
    return IRQ_HANDLED;
}

/* Top-half: 在硬中斷 Context 執行，不能睡眠 */
static irqreturn_t my_hard_irq(int irq, void *dev_id)
{
    /* 快速判斷是否是我的中斷 */
    /* 如果需要，讀取/清除狀態暫存器 */
    
    /* 喚醒 Thread 處理剩下的事 */
    return IRQ_WAKE_THREAD;
}

static int my_probe(struct platform_device *pdev)
{
    /* 申請 IRQ，並設定 ONESHOT (必要的) */
    return devm_request_threaded_irq(&pdev->dev, irq,
                                     my_hard_irq,
                                     my_thread_fn,
                                     IRQF_ONESHOT,
                                     "my-device", priv);
}
```

### 2. Bottom-half 機制大亂鬥

面試必考：要在這麼多機制中選哪個？

| 機制 | Context | 可睡眠? | 用途 | 推薦度 |
| :--- | :--- | :--- | :--- | :--- |
| **Softirq** | Softirq | ❌ | 網卡、高頻區塊設備 (核心內部用) | 🚫 驅動別用 |
| **Tasklet** | Softirq | ❌ | 舊驅動的輕量任務 | ⚠️ Deprecated |
| **Workqueue** | Process | ✅ | 需要延遲執行、長時間 I/O | ✅ 常用 |
| **Threaded IRQ** | Process | ✅ | **中斷處理的標準解法** | 🏆 首選 |

### 3. Concurrency 與鎖的選擇

在中斷中寫 code 最容易踩到的坑就是 Locking。

#### 規則：
1.  **Interrupt Context (Top-half/Softirq/Tasklet)**:
    -   ❌ **絕對不能睡眠** (不能呼叫 `mutex_lock`, `msleep`, `kmalloc(GFP_KERNEL)`).
    -   ✅ 只能用 `spinlock` (且需注意是否需關中斷 `spin_lock_irqsave`).
    -   ✅ 只能用 `GFP_ATOMIC` 分配記憶體.

2.  **Process Context (Workqueue/Threaded IRQ)**:
    -   ✅ 可以睡眠.
    -   ✅ 可以用 `mutex`.

#### 檢查 Context 的 API

```c
if (in_interrupt()) {
    /* 這是中斷 context，小心！ */
}
```

## 🔷 Logic II: GIC 硬體架構 (ARM)

**GIC (Generic Interrupt Controller)** 是 ARM 系統的中斷管家。

### 1. 硬體架構圖 (GICv2 vs GICv3)

```text
[Peripherals] --> [Distributor] --> [CPU Interface] --> [CPU Core]
                      ↑                  ↑
             (負責分發、優先級排序)   (負責通知 CPU)
```

**GICv3 的改進**:
-   新增 **Redistributor**: 每個 CPU 專屬一份，解決多核競爭瓶頸。
-   支援 **LPI (Locality-specific Peripheral Interrupts)**: 訊息基底中斷 (MSI)，數量可達數萬。
-   使用 **System Register** 存取 (而非 MMIO)，速度更快。

### 2. 中斷類型 (Types)

面試常問：「GIC 的 PPI 和 SPI 有什麼差別？」

| 類型 | 全名 | 範圍 (ID) | 描述 | 範例 |
| :--- | :--- | :--- | :--- | :--- |
| **SGI** | Software Generated | 0-15 | 軟體觸發，用於 CPU 間通訊 (IPI) | Task 排程 |
| **PPI** | Private Peripheral | 16-31 | 私有中斷，每個 CPU 獨立 | Local Timer, PMU |
| **SPI** | Shared Peripheral | 32-1019 | 共享中斷，可分發給任一 CPU | UART, GPIO, I2C |
| **LPI** | Locality-specific | 8192+ | (GICv3) 訊息中斷 | PCIe MSI-X |

### 3. 中斷親和性 (SMP Affinity)

在多核心系統中，我們可以指定某個 IRQ 給特定的 CPU 處理，以優化效能。

**優點：**
1.  **Cache Locality**: 資料留在該 CPU 的 Cache 中。
2.  **Load Balancing**: 手動分散負載，避免 CPU0 忙死。

**操作：**
```bash
# 查看 IRQ 33 當前由誰處理
cat /proc/irq/33/smp_affinity

# 指定由 CPU 2 處理 (遮罩 0x4 = 0100)
echo 4 > /proc/irq/33/smp_affinity
```

## 🔷 Logic III: 進階話題 & 優化

### 1. 中斷延遲 (Latency) 分析

從硬體發生信號到 ISR 第一行程式碼執行的時間。

**組成：**
1.  **Hardware**: 信號傳輸 + GIC 判斷。
2.  **CPU**: 完成當前指令 + Pipeline Flush + Mode Switch。
3.  **Kernel**: Vector Table 跳轉 + Context Save (`handle_arch_irq`).

**如何量測？**
最準確的方法：**GPIO Toggle + 示波器**。
在 ISR 第一行拉高 GPIO，結束時拉低。量測觸發訊號到 GPIO 拉高的時間差。

### 2. PREEMPT_RT (Real-Time Linux)

在 RT Kernel 中，中斷處理發生了質變：
-   **Forced Threading**: 幾乎所有的 HardIRQ 都強制轉為 Threaded IRQ 執行。
-   **Spinlock 變 Mutex**: `spinlock_t` 被替換為可睡眠的 `rt_mutex`，以允許高優先級任務搶占。

這就是為什麼在寫驅動時，盡量用 Threaded IRQ 和 Spinlock (不要 Disable IRQ 太久)，你的驅動才能在 RT 系統上運作良好。

### API Cheat Sheet

| 需求 | API |

| **申請中斷 (現代)** | `devm_request_threaded_irq(dev, irq, top, bot, flags, name, data)` |

### Trigger Flags (`request_irq` flags)

| Flag | 意義 |
| :--- | :--- |
| `IRQF_TRIGGER_RISING` | 上升緣觸發 (GPIO 常見) |
| `IRQF_TRIGGER_LEVEL_HIGH` | 高電平觸發 (PCIe/共享中斷常見) |
| `IRQF_SHARED` | 允許多個裝置共用此 IRQ |
| `IRQF_ONESHOT` | Thread 結束前保持 Mask (Threaded IRQ 必備) |

## 📝 精選面試題 (Interview Questions)

### Q1: Top-half 和 Bottom-half 有什麼區別？
-   **Top-half**: 負責「緊急且快速」的工作。在 HardIRQ Context，關中斷，不可睡眠。主要工作是 Ack 硬體、Copy 少量資料、喚醒 Bottom-half。
-   **Bottom-half**: 負責「耗時」的工作。在 Process/Softirq Context，開中斷，可睡眠 (Thread/WQ)。主要工作是資料處理、複雜運算。

### Q2: 為什麼在 Interrupt Context 不能使用 Mutex？
-   `mutex_lock` 在拿不到鎖時會讓當前 Process 進入睡眠 (Sleep)。
-   Interrupt Context (Top-half) 不屬於任何 Process，沒有 `task_struct` 可以被排程出去再喚醒。
-   一旦睡眠，就沒人能喚醒它，導致系統死鎖或 Kernel Panic。

### Q3: 什麼是 Spurious Interrupt (鬼中斷)？
-   **現象**: CPU 收到中斷信號，但檢查所有周邊，發現沒人觸發。
-   **原因**: 電氣雜訊、信號時序問題 (Line Glitch)，或是 ISR 處理完但沒有正確清除 Hardware Flag，導致一開中斷又觸發。
-   **處理**: Kernel 有計數器監視，如果某個 IRQ 瘋狂觸發卻沒人認領 (Unprobed)，Kernel 會自動 Disable 該 IRQ 以免死機。

### Q4: 解釋 IRQF_ONESHOT 的用途？
-   在使用 **Threaded IRQ** 時，Top-half 若設為 NULL (或很短)，硬體中斷可能還沒被清除 (通常在 Thread 中才清除)。
-   如果是 **Level Trigger**，一退出 Top-half，Level 還是 High，就會再次觸發中斷，導致無限迴圈 (Interrupt Storm)，Thread 永遠沒機會執行。
-   `IRQF_ONESHOT` 告訴 Kernel：**「在 Thread 跑完之前，不要打開這個 IRQ！」** 確保 Thread 有機會去清除中斷源。

### Q5: GIC 的 IAR 和 EOI 暫存器是用來做什麼的？
-   **IAR (Interrupt Acknowledge Register)**: CPU 讀取它來「認領」中斷，並獲取 IRQ ID。讀取的瞬間，該中斷狀態變為 **Active**。
-   **EOI (End of Interrupt Register)**: CPU 寫入它來「告知」GIC 中斷處理完畢。寫入後，狀態變回 **Inactive** (或 Priority Drop)，允許同優先級或更低優先級的中斷再次發生。
