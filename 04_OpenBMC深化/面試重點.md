**IPMI 安全性問題（面試必知！）：**
> [!WARNING]
> **IPMI 安全性弱點（為什麼要用 Redfish 取代）**
> 
> 1. **Cipher Suite 0 漏洞 (CVE-2013-4786)**
>    - 允許無認證存取！很多實作預設啟用。
> 2. **IPMI v1.5 密碼問題**
>    - 密碼以明文或弱加密傳輸，容易被嗅探。
> 3. **IPMI v2.0 RMCP+ 仍有問題**
>    - RAKP 協定有已知弱點，密碼 Hash 可被離線暴力破解。
> 4. **預設密碼**
>    - 很多 BMC 使用預設的 `admin/admin`。
> 
> **結論**：在安全敏感環境，應該使用 **Redfish (HTTPS)** 取代 IPMI。

### IPMI 底層：KCS (Keyboard Controller Style) 原理解析

#### 🎯 面試重點 (Context)
面試官問：「當 OS 網路還沒通，或是網路壞掉時，要怎麼跟 BMC 溝通？」
這時候就需要 **System Interface**。
KCS 是最古老但也最常見的介面。它的設計源自於早期的「鍵盤控制器」，所以叫 Keyboard Controller Style。
它不依賴網路，而是透過主機板上的線路 (LPC Bus) 直接傳訊號。

#### 🧠 心智模型 (Mental Model)
想像 Host CPU 和 BMC 之間隔著一道牆，牆上只有兩個小信箱：
1.  **Input 信箱 (IDR)**：CPU 塞東西進去，BMC 拿出來。
2.  **Output 信箱 (ODR)**：BMC 塞東西進去，CPU 拿出來。
3.  **狀態旗標 (Status)**：信箱旁有旗子（IBF/OBF），表示「信箱滿了」或「信箱空了」。

**硬體傳輸圖解：**
```
      Host CPU (x86/ARM)                       BMC (ASPEED)
     ┌──────────────────┐                     ┌──────────────────┐
     │  OS / Driver     │                     │  IPMI Daemon     │
     └────────┬─────────┘                     └────────┬─────────┘
              │ 寫入 I/O 0xCA2                         │ 讀取 Register
              ▼                                        ▼
     ┌──────────────────┐                     ┌──────────────────┐
     │ LPC Interface    │ <---- LPC Bus ----> │ LPC Controller   │
     └────────┬─────────┘                     └────────┬─────────┘
              │                                        │
           [ IBF ] (Input Buffer Full?) <--------------┘
              │
           [ OBF ] (Output Buffer Full?) --------------> 
```text

#### ⚙️ 核心邏輯：Handshake 流程 (Flow)
因為一次只能傳 1 個 byte，所以需要嚴格的「你丟我撿」流程：

1.  **Wait**: Host 檢查 `IBF` (Input Buffer Full) 是否為 0？（確認信箱是空的，BMC 拿走上次的信了沒？）
2.  **Write**: Host 把資料寫入 Data Register。
3.  **Set**: 硬體自動把 `IBF` 設為 1。（旗子立起來，通知 BMC 有信）
4.  **Process**: BMC 看到 `IBF=1`，把資料讀走，硬體自動把 `IBF` 歸 0。

**KCS 狀態機流程：**
Write Start (0x61) -> 等待 IBF=0 -> 寫 NetFn -> 寫 Command -> 寫 Body -> Write End (0x62) -> 讀 Response

---

### IPMI 底層：BT (Block Transfer) 差異
KCS 像傳紙條（一次一個字），BT 就像「傳包裹」。
BT 有專屬的 Buffer，可以一次把整串 IPMI 指令寫進去，再一次通知 BMC。效率比 KCS 高，但硬體成本稍高。

#### 📚 附錄：KCS 暫存器定義 (Reference)
（寫 Driver 時再查閱此表，面試不用背）

**Status Register (I/O Offset + 1)**
說明：Host 讀取此暫存器來判斷能不能寫入。
| Bit | Name | 意義 | 邏輯 |
|:---|:---|:---|:---|
| 7:6 | State | 狀態機 | 00=Idle, 01=Read, 10=Write |
| 3 | CD | Command/Data | 1=這是指令, 0=這是資料 |
| 2 | **IBF** | Input Buffer Full | 1=Host已寫入，BMC尚未讀取 (Host要等) |
| 0 | **OBF** | Output Buffer Full| 1=BMC已寫入，Host尚未讀取 (Host可讀) |

**Linux Driver 位置**
- `drivers/char/ipmi/ipmi_kcs_sm.c`: KCS 狀態機邏輯
- `drivers/char/ipmi/ipmi_si_intf.c`: 底層 I/O 操作

### IPMI OEM Command 設計

```c
/* OEM Command 範例 - Meta/Facebook 風格 */

/* OEM NetFn 定義 */
#define NETFN_OEM              0x30      /* Meta 使用 0x30 */
#define NETFN_OEM_NVIDIA       0x3C      /* NVIDIA 使用 0x3C */

/* OEM Command 結構 */
/*
 * Request:
 *   Byte 1-3: Manufacturer ID (IANA Number)
 *             Meta = 0x00 0x75 0x4B (0x4B7500)
 *   Byte 4:   OEM Command Code
 *   Byte 5+:  Command-specific Data
 *
 * Response:
 *   Byte 1:   Completion Code
 *   Byte 2-4: Manufacturer ID (Echo)
 *   Byte 5+:  Response Data
 */

/* 範例：讀取 Meta 平台特定資訊 */
/* Request: 30 00 4B 75 00 01  (NetFn=0x30, CMD=0x00, IANA=Meta, SubCmd=0x01) */

/* OpenBMC OEM Handler 實作位置 */
/* openbmc/phosphor-host-ipmid 中的 oemhandler.cpp */

/* 實作範例 */
namespace ipmi
{

static ipmi::RspType<uint8_t, std::vector<uint8_t>>
    oemGetPlatformId(ipmi::Context::ptr ctx)
{
    // 回傳平台識別碼
    std::vector<uint8_t> platformId = {0x59, 0x34};  // "Y4" = Yosemite 4
    return ipmi::responseSuccess(0x00, platformId);
}

void registerOemFunctions()
{
    ipmi::registerHandler(ipmi::prioOemBase,
                          NETFN_OEM,
                          CMD_OEM_GET_PLATFORM_ID,
                          ipmi::Privilege::Admin,
                          oemGetPlatformId);
}

} // namespace ipmi
```

### IPMI SDR (Sensor Data Record) 結構

```c
/* SDR 用於描述系統中的感測器 */

/* SDR Header (所有 SDR 都有) */
struct sdr_header {
    uint16_t record_id;      /* Record ID (動態分配) */
    uint8_t  sdr_version;    /* SDR Version (0x51 for IPMI 2.0) */
    uint8_t  record_type;    /* Type 01=Full, 02=Compact, 03=Event-Only */
    uint8_t  record_length;  /* 後續資料長度 */
} __attribute__((packed));

/* SDR Type 01: Full Sensor Record (最常見) */
struct sdr_full_record {
    struct sdr_header header;
    
    /* Key (用於識別感測器) */
    uint8_t  owner_id;       /* Sensor 所屬的 Slave Address */
    uint8_t  owner_lun;      /* LUN */
    uint8_t  sensor_number;  /* Sensor Number (唯一識別) */
    
    /* Entity Information */
    uint8_t  entity_id;      /* 0x07=System Board, 0x0B=Add-in Card */
    uint8_t  entity_instance;
    
    /* Sensor Info */
    uint8_t  sensor_init;    /* 初始化設定 */
    uint8_t  sensor_caps;    /* 能力 (Threshold support) */
    uint8_t  sensor_type;    /* 0x01=Temperature, 0x02=Voltage */
    uint8_t  event_type;     /* Event/Reading Type */
    
    /* Thresholds */
    uint8_t  upper_critical;
    uint8_t  upper_non_critical;
    uint8_t  lower_non_critical;
    uint8_t  lower_critical;
    
    /* Conversion Formula: y = (M * x + B) * 10^K */
    uint8_t  m_lsb;          /* M 值低 8 位 */
    uint8_t  m_msb_tolerance;
    uint8_t  b_lsb;          /* B 值低 8 位 */
    uint8_t  b_msb_accuracy;
    uint8_t  r_exp_b_exp;    /* 指數 K */
    
    /* Sensor Name (最多 16 bytes) */
    uint8_t  id_type_len;    /* Bit 7:6 = Type, Bit 4:0 = Length */
    char     id_string[16];  /* Sensor 名稱 */
} __attribute__((packed));

/* ipmitool 讀取 SDR 範例 */
/*
 * $ ipmitool sdr list
 * CPU0 Temp        | 45 degrees C    | ok
 * Inlet Temp       | 28 degrees C    | ok
 * PSU0 Power       | 350 Watts       | ok
 * Fan0             | 6000 RPM        | ok
 *
 * $ ipmitool sdr get "CPU0 Temp"
 * Sensor ID              : CPU0 Temp (0x01)
 * Entity ID              : 7.1 (System Board)
 * Sensor Type            : Temperature
 * Sensor Reading         : 45 (+/- 0) degrees C
 * Status                 : ok

 * Upper critical         : 90.000
 */
```

### Redfish（面試必考！）

Redfish 是 DMTF 制定的現代 RESTful API 標準（2015年）。
目標是取代 IPMI，成為伺服器管理的新標準。

**Redfish 架構圖：**
### Redfish (現代化管理協定) 解析

#### 🎯 面試重點 (Context)
面試官問：「為什麼現在 Server 都用 Redfish 而不用 IPMI？」
答案：**標準化與現代化**。
Redfish 是 Server 管理的「RESTful API」。
它解決了 IPMI 的三大痛點：
1. **安全性**：IPMI 明文傳輸太危險，Redfish 走 HTTPS。
2. **描述力**：IPMI 只有簡單數值，Redfish 有階層結構 (JSON)。
3. **擴充性**：IPMI 依賴 OEM Command，Redfish 有標準 Schema。

#### 🧠 心智模型 (Mental Model)
**1. 資源樹 (Resource Tree)**
想像 Redfish 就像一個**檔案系統**或**網站目錄**。
一切都從根目錄 `/redfish/v1/` 開始。
```
/redfish/v1/
 ├── Systems/ (邏輯視角：OS、CPU、RAM)
 │    └── system/
 │         ├── Processors/
 │         ├── Memory/
 │         └── Actions/ (開關機)
 ├── Chassis/ (物理視角：機殼、風扇、電源)
 │    └── chassis/
 │         ├── Thermal/ (溫度、風扇)
 │         └── Power/ (電壓、PSU)
 └── Managers/ (管理視角：BMC 本身)
      └── bmc/
           ├── LogServices/
           └── NetworkProtocol/
```text

**2. 事件通知比喻 (Eventing)**
BMC 發生大事（如過熱）要怎麼通知 User？有兩種模式：

*   **SSE (Server-Sent Events) - 訂閱雜誌模式**
    *   **機制**：Client 建立連線後，BMC 有事直接推播。
    *   **比喻**：你訂閱了雜誌，出版社每個月**主動寄**給你，不用你每天去書店問。
    *   **推薦**：適合 Dashboard 或瀏覽器監控。

*   **Webhook - 留電話模式**
    *   **機制**：BMC 主動發 POST 到你指定的 URL。
    *   **比喻**：你修車留**電話號碼**，老闆修好**主動打給你**。
    *   **限制**：如果你的電話打不通（防火牆擋住），老闆就聯絡不到你。

#### ⚙️ 核心邏輯：常用操作 (Flow)

**1. 讀取資訊 (GET)**
取得 CPU 溫度：

### Redfish 深入：Session 認證

Redfish 支援多種認證方式：

1. Basic Authentication
   - Header: Authorization: Basic base64(user:pass)
   - 每次請求都帶密碼
   - 簡單但不安全

2. Session Token
   - 先 POST /redfish/v1/SessionService/Sessions 取得 Token
   - 之後用 X-Auth-Token Header
   - 推薦方式

3. OAuth 2.0 / MTLS
   - 進階認證方式
   - 部分實作支援

**Session 認證流程：**
```bash
# 1. 建立 Session
curl -k -X POST \
  -H "Content-Type: application/json" \
  -d '{"UserName": "root", "Password": "0penBmc"}' \

# 回應 Header 包含：
# X-Auth-Token: <token-value>
# Location: /redfish/v1/SessionService/Sessions/abcd1234

# 2. 使用 Token 存取 API
curl -k -H "X-Auth-Token: <token-value>" \
  https://bmc-ip/redfish/v1/Systems/system

# 3. 登出（刪除 Session）
curl -k -X DELETE \
  -H "X-Auth-Token: <token-value>" \

### PLDM (Platform Level Data Model) 解析

#### 🎯 面試重點 (Context)
面試官問：「Redfish 是給人看的，那機器之間用什麼溝通？」
答案就是 **PLDM**。
PLDM 是 Server 內部的「通用語言」。不管底層是 I2C (SMBus)、PCIe (VDM) 還是 USB，上層都講 PLDM。
**最核心的應用**：
1. **監控** (Type 2)：BMC 讀取 GPU 溫度。
2. **韌體更新** (Type 4)：BMC 幫網卡/GPU 更新韌體。
3. **BIOS 溝通** (Type 5)：BIOS 和 BMC 交換設定。

#### 🧠 心智模型 (Mental Model)
**1. 俄羅斯娃娃結構**
PLDM 封包是「寄生」在 MCTP 封包裡的。
PLDM 就像應用層協定 (HTTP)，MCTP 就像傳輸層 (TCP/IP)。

**2. 協定堆疊 (Protocol Stack)**
```
┌─────────────────────────────────────────────────────────────┐
│                    PLDM/MCTP 協定堆疊                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Application Layer                                          │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  PLDM Types (各種功能)                               │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐  │   │
│  │  │Type0│ │Type1│ │Type2│ │Type3│ │Type4│ │Type5│  │   │
│  │  │Base │ │SMBIO│ │Monit│ │BIOS │ │FW   │ │FRU  │  │   │
│  │  └─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘  │   │
│  └─────────────────────────────────────────────────────┘   │
│                            ▲                                │
│                            │                                │
│  Transport Layer           │                                │
│  ┌─────────────────────────┴───────────────────────────┐   │
│  │                      MCTP                            │   │
│  │  (封包格式、定址、分片/重組)                         │   │
│  └─────────────────────────┬───────────────────────────┘   │

#### ⚙️ 核心邏輯：PLDM 運作流程 (Flow)
**1. 發現階段 (Discovery)**
- BMC 問裝置：「你是誰？」(GetTID)
- BMC 問裝置：「你會什麼語言？」(GetPLDMTypes)
- BMC 問裝置：「有哪些指令？」(GetPLDMCommands)

**2. 描述階段 (PDR Repository)**
- BMC 就像爬蟲，把裝置的 PDR (Platform Descriptor Record) 全部抓回來。
- PDR 就像「說明書」，定義了：「Sensor ID 1 號是溫度，單位是度 C」。

**3. 運作階段 (Operation)**
- **讀取 Sensor**：BMC 發送 `GetSensorReading` (透過 Sensor ID)。
- **更新 FW**：BMC 傳送 Firmware 封包。

#### 🔍 深入解析 (Deep Dive)

| Type | 名稱 | 用途 |

| Type 2 | Monitoring | Sensor 讀取、PDR |
| Type 3 | BIOS Control | BIOS 表格設定 |

### SPDM (Security Protocol and Data Model) 解析

#### 🎯 面試重點 (Context)
面試官問：「你怎麼確定插在伺服器上的那張 H100 GPU 是真的 NVIDIA 出廠的，而不是被駭客竄改過的假貨？」
這就是 **Supply Chain Security** 的核心問題。
SPDM 就像是「數位護照查驗」。
BMC (Requester) 會要求 GPU (Responder) 出示護照 (Certificate)，並且簽名 (Challenge_Auth) 證明它是本人。
這在 NVIDIA/AMD 的高階 AI 伺服器中是 **Standard Requirement**。

#### 🧠 心智模型 (Mental Model)
**查驗護照流程：**
1. **GET_VERSION**: 「請問你是講哪國語言？」(SPDM 1.0, 1.1, 1.2?)
2. **GET_CAPABILITIES**: 「你有護照嗎？你會簽名嗎？」
3. **GET_DIGESTS**: 「給我看你的護照縮圖 (Hash)。」
4. **GET_CERTIFICATE**: 「給我完整的護照 (X.509 Cert)。」
5. **CHALLENGE**: 「隨便唸這串亂碼 (Nonce)，並用你的私鑰簽名。」(證明你擁有私鑰，不是撿別人的護照來用)
6. **GET_MEASUREMENTS**: 「讓我檢查你的行李 (Firmware Hash)。」(確保韌體沒被偷改)

**憑證信任鏈 (Chain of Trust):**
```
ROOT CA (NVIDIA) ─(簽章)→ Intermediate CA ─(簽章)→ Device Cert (GPU)
   ↑ 
(BMC OTP 內存有 Root CA 的 Hash，以此為信任根源)
```

#### ⚙️ 核心邏輯：驗證流程 (Flow)
1. **啟動階段**：系統上電。
2. **發現階段**：BMC 透過 MCTP 找到 GPU。
3. **認證階段 (SPDM)**：執行上述 5 步驟交換。
    - 若失敗 → BMC 判定該裝置不安全 → 禁止開機或斷電。
4. **測量階段 (Measurement)**：BMC 讀取 GPU 韌體 Hash，比對 "Golden Measurement"。
    - 若不符 → 判定韌體遭竄改。

#### 📚 參考資料：libspdm 實作 (Reference)
**初始化 SPDM Context (C Code 範例)**
```c
/* 使用 libspdm 進行認證的標準寫法 */
/* 來源：openbmc/libspdm */

libspdm_return_t authenticate_device(void *ctx)
{
    /* 1. 交換版本 */
    libspdm_get_version(ctx, ...);
    
    /* 2. 交換能力 */
    libspdm_get_capabilities(ctx, ...);
    
    /* 3. 協商演算法 */
    libspdm_negotiate_algorithms(ctx, ...);
    
    /* 4. 取得憑證鏈 */
    libspdm_get_certificate(ctx, ...);
    
    /* 5. 挑戰回應 (關鍵驗證！) */
    /* Nonce 會由 Library 自動產生 */
    status = libspdm_challenge(ctx, ..., measurement_hash, ...);
    
    if (status != LIBSPDM_STATUS_SUCCESS) {
        printf("Security Alert: Device authentication failed!\n");
        return status;
    }
    return LIBSPDM_STATUS_SUCCESS;
}
```

### 🧩 BMC 硬體介面總覽 (Hardware Knowledge)

#### 🎯 面試重點 (Context)
面試官問：「BMC 透過什麼介面控制電源？」或「如何讀取 CPU 溫度？」
這是在考你對 **BMC SoC 與周邊硬體連接** 的理解。
BMC 不只是一個軟體，它是一顆有很多「觸手」的控制器。

#### 🧠 心智模型 (Mental Model)
**八爪章魚 (The Octopus)：**
想像 BMC 是一隻章魚，每一隻觸手 (Interface) 抓住主機板上的一個重要器官：
- **觸手 A (GPIO)**：按住電源鍵 (Power Button)。
- **觸手 B (I2C/SMBus)**：拿聽診器貼在 CPU/GPU 上聽心跳 (溫度/電壓)。
- **觸手 C (LPC/eSPI)**：甚至接管了 BIOS 的串口 (SOL)。
- **觸手 D (PCIe)**：這是最粗的一根血管，用來傳輸大量影像 (KVM) 或數據 (DMA)。

#### 🔍 介面詳解 (Deep Dive)

| 介面 (Interface) | 頻寬 | 用途 (Use Case) | 關鍵訊號 / 裝置 |
| :--- | :--- | :--- | :--- |
| **I2C / SMBus** | 低 | **感測器讀取**、FRU 讀取 | Temp Sensor, PSU, EEPROM, Fan |
| **GPIO** | 極低 | **開關控制**、中斷訊號 | Power_Btn, Reset_Btn, PROCHOT, LED |
| **LPC / eSPI** | 中 | **Host 通訊** legacy 通道 | KCS (IPMI), Post Code, SuperIO |
| **PCIe** | 極高 | **高速通訊** | VGA (KVM), DMA (P2A) |
| **UART** | 低 | **除錯與 Console** | BMC Console, Host SOL |
| **SPI** | 中 | **韌體存儲** | BMC Flash, Host BIOS Flash |
| **PECI** | 中 | **Intel CPU 專用** | CPU Temp, Power limitiation |
| **JTAG** | 低 | **硬體除錯** | CPLD update, Chip internal state |

#### ⚠️ 硬體互動安全規範 (Safety Rules)
1. **確認 SoC 型號**：AST2500, AST2600, AST1030 暫存器位置不同。
2. **禁止猜測**：操作 `devmem` 或 `i2cset` 前，務必查 Datasheet 或 Device Tree。
3. **破壞性操作**：亂寫 GPIO 可能導致短路或不預期關機。

    3. 提供故障診斷和回復機制
    4. 支援大規模數據中心的自動化管理

    BMC 讓管理者不需要實體接觸伺服器就能進行管理操作。

**Q1-1：請解釋 In-band 和 Out-of-band Management 的差異？**
*   **A**: 核心差異在於「是否依賴作業系統」來管理伺服器。

    1. In-band Management (帶內管理)：
       - 依賴 OS (Windows/Linux) 運作。
       - 使用 Host 端的網路 (LAN) 和軟體 (SSH, RDP, Agent)。
       - 缺點：OS 當機或網路斷線時無法救援。

    2. Out-of-band Management (帶外管理, OOB)：
       - 不依賴 OS，由 BMC 晶片獨立運作及供電。
       - 使用獨立或共享的 BMC 網路通道。
       - 優點：即使 OS 藍屏 (BSOD)、關機或硬碟損壞，仍可控制。

    常見 OOB應用場景：
    - 遠端電源控制 (Power Cycle)：解決死機問題。
    - KVM over IP：遠端看 BIOS 畫面、POST代碼。
    - Virtual Media：遠端掛載 ISO 檔重灌系統。



    問：
    「為什麼我們需要 Out-of-band management？」或者「BMC 提供了什麼價值？」

    答：
    「Out-of-band management 讓系統管理員可以在伺服器及其作業系統完全失效 (BSOD/Kernel Panic) 或關機的狀態下，仍然能透過獨立的 BMC 網路通道進行救援、重啟或重新安裝系統。這對於大規模資料中心的自動化維運至關重要，因為我們無法派人去現場按每一台機器的電源鍵。」

### 技術補充 (加分題)

1. 獨立通道：
   - OOB 通常使用與 Host OS 分開的網路介面 (Dedicated Mgmt Port)，或者透過 NC-SI 技術共享網孔 (Shared NIC)。
   - 流量在網卡內部就會分流給 BMC，不會進入 Host OS，確保了這條通道的獨立性與安全性。

2. 安全隱憂：
   - 因為 OOB 權限極大（能控制電源、看畫面），所以現在非常重視安全性（Secure Boot, PFR, 權限控管）。
   - 這也是為什麼 IPMI 逐漸被 Redfish (HTTPS) 取代的原因之一。


**Q2：你在 OpenBMC 中做過什麼？**

**Q5：如何處理 sensor 讀取問題？**
*   **A**: Debug 步驟：

    1. 確認硬體連接
       - i2cdetect 看 device 有沒有出現
   
    2. 確認 driver 載入（關鍵！）

    3. 確認 sysfs

    4. 確認 D-Bus
       - busctl get-property ...

    5. 確認 Redfish/IPMI
       - curl Redfish API
       - ipmitool sensor list

### 觀念釐清：Driver Loading 常見誤區

這是在底層驅動面試中非常容易被混淆的觀念，請務必搞清楚。

#### 1. Built-in (`=y`) vs Loadable Module (`=m`)
這是 Kernel Compile (`make menuconfig`) 時的設定差異。

| 特性 | Built-in (`=y`) | Loadable Module (`=m`) |
| :--- | :--- | :--- |
| **存在形式** | 直接編譯在 Kernel Image 內 | 獨立的 `.ko` 檔案 (在 `/lib/modules`) |
| **記憶體** | 開機即佔用，直到關機 | 需要時才載入 `insmod`，不用時可卸載 `rmmod` |
| **lsmod** | **看不見** (因為是一體的) | **看得見** |
| **OpenBMC** | **90% 都是這一類** (穩定/快速) | 少用，多用於 Debug 或非必要周邊 |

**迷思**：「我看不到 `.ko` 檔或是 `lsmod` 沒東西，就是沒 Driver？」
**修正**：錯！OpenBMC 大多數 Driver (如 `lm75`, `tmp421`) 都是 Built-in 的。

#### 2. Device Tree (DTS) 的角色
DTS 是一份**「靜態硬體點名簿」**。
*   它告訴 Kernel：「這裡有一個硬體叫做 `compatible = "aspeed,ast2600-i2c"`」。
*   **重點**：DTS 裡的裝置，其 Driver **可以是 Built-in 也可以是 Module**。
*   **流程**：Kernel 開機 → 讀取 DTS → 發現裝置 → 在已載入的 Driver 中尋找配對 → 執行 `probe`。

#### 3. Entity-Manager 的角色
Entity-Manager 是一個**「動態硬體點名員」** (User Space Service)。
*   **場景**：Riser Card 或 Backplane 這種**開機時不一定存在**的硬體。
*   **流程**：Entity-Manager 讀取 FRU → 辨識出硬體 → 通知 Kernel 建立裝置 (Instantiate)。
*   **迷思**：「Entity-Manager 掃描到才去 Load Driver？」
*   **修正**：錯！通常 Driver (如 `tmp75`) **早就以 Built-in 的形式存在 Kernel 裡等待了**。Entity-Manager 只是觸發「裝置生成實例」，讓 Driver 有工作做而已。

#### 4. 面試回答策略
> 「Device Tree 定義**靜態**存在的硬體，Entity-Manager 處理**動態**發現的硬體。
> 至於 Driver 是 Built-in 還是 Module，取決於編譯設定。
> 在 OpenBMC 中，為了確保感測器隨插即用且穩定，這類 Sensor Driver 通常都編譯為 **Built-in**。」

#### 5. 深入解析：Device Instantiation (裝置實例化)

這是 Linux Driver Model 的核心觀念，懂這個能證明你不是只會抄 code。

**觀念比喻：**
*   **Driver Loading (載入驅動)**：
    *   像是「聘請了一位水電工 (Driver)」，他懂修國際牌冷氣。此時他只是在辦公室喝茶 (Memory Resident)。
    *   對應：`insmod` 或 `Built-in`。
*   **Device Instantiation (裝置實例化)**：
    *   像是「開了一張維修單 (Instance)」，上面寫著「3 樓會議室 (Bus 3) 的角落 (Address 0x48) 有一台國際牌冷氣」。
    *   對應：DTS 定義或 Entity-Manager 生成。
*   **Binding (配對)**：
    *   工廠主管 (Kernel) 看到單子，叫水電工去現場。這時水電工才真正開始工作 (`probe`)。

**技術定義：**
Instantiation 就是在 Kernel Space 建立一個代表該硬體的 `struct device` (如 `i2c_client`)。常見方式有二：

1.  **Static (DTS)**：
    *   寫在 `.dts` 檔。開機時 Kernel 自動讀清單並實例化。
    *   適用：主機板上焊死的 IC。

2.  **User-space (sysfs)  Entity-Manager 用的方法**：
    *   指令：`echo tmp75 0x48 > /sys/bus/i2c/devices/i2c-1/new_device`
    *   告訴 Kernel 在指定位置生成實例，Kernel 隨即喚醒 Driver 進行 probe。

**結論**：Driver 載入不代表會工作，必須要有 Device Instantiation 才會觸發 probe。


**Q6：什麼是 Secure Boot？BMC 如何實現？**
*   **A**: Secure Boot 確保只有經過簽章驗證的程式碼才能執行。

    BMC Secure Boot 流程：
    1. Boot ROM 驗證 SPL/U-Boot
    2. U-Boot 驗證 Kernel (FIT image)
    3. Kernel 驗證 rootfs (可選)

    實作方式：
    - 使用非對稱加密（RSA/ECDSA）
    - 公鑰燒錄在 OTP (One-Time Programmable) 記憶體
    - 每一層都驗證下一層的簽章

    OpenBMC 支援通過 Phosphor-software-manager 進行簽章驗證。

### 🏆 一線外商攻略 (NVIDIA / AMD)

#### 🎯 戰略分析 (Context)
為什麼這兩家公司都在找 BMC 工程師？
- **NVIDIA**: 因為 HGX/DGX 系統太複雜，GPU 功耗與熱量巨大，BMC 必須精準控制。
- **AMD**: 因為 EPYC 在 Server 市場攻城略地，且極度重視平台安全性 (Platform Security)。

#### 🧠 差異化模型 (Mental Model)
| 特性 | NVIDIA (GPU 導向) | AMD (CPU 導向) |
| :--- | :--- | :--- |
| **核心戰場** | **Thermal & Telemetry** | **Security & RoT** |
| **關鍵協定** | PLDM (Type 2/4), MCTP | SPDM, Secure Boot |
| **痛點** | GPU 過熱、NVLink 錯誤 | Bios 被竄改、供應鏈攻擊 |
| **代表產品** | HGX H100, DGX, Grace | EPYC Genoa/Turin, MI300 |

#### ⚔️ NVIDIA 攻略戰術
**關鍵字：Thermal, PLDM, Telemetry**
1. **GPU 監控是核心**：
   - 透過 PLDM over MCTP (PCIe/SMBus) 抓取 GPU 溫度與狀態。
   - 必須熟悉 **Thermal Throttling** 流程：`Warning` -> `Fan Up` -> `Critical` -> `Throttling` -> `Shutdown`。
2. **NVLink 拓撲**：
   - 不只是看單顆 GPU，要看整堆 GPU 怎麼連。NVLink Error 會導致訓練中斷，BMC 需即時回報。
3. **Telemetry (遙測)**：
   - 資料中心需要即時數據。必讀 **Redfish Telemetry Service**。

#### 🛡️ AMD 攻略戰術
**關鍵字：Security, RoT, PSP**
1. **Security First**：
   - AMD 平台極度依賴 **PSP (Platform Security Processor)**。
   - BMC 必須配合 PSP 進行 Secure Boot 驗證，確保開機鏈信任。
2. **Root of Trust (RoT)**：
   - 面試必問：「什麼是 RoT？誰是這一台機器的 RoT？」
   - 通常是 **H/W RoT** (Boot ROM + OTP Fuse)，不可被軟體修改。
3. **OpenBMC 實作**：
   - 熟悉 `phosphor-secure-upload` 等安全更新機制。

#### 💾 Intel 補充
雖然 Intel 不做 BMC SoC (主要由 ASPEED 獨佔)，但 Intel 制定了 x86 Server 標準，影響力仍在。
- **PECI**：Intel 獨有的 CPU 管理介面 (Sideband)，讀取溫度與錯誤 (RAS)。
- **RAS**：Reliability, Availability, Serviceability。Intel 平台非常強調硬體錯誤處理 (MCA, AER)。

### Q1：解釋 KCS 和 BT Interface 的差異

**難度**：⭐⭐⭐⭐
**常見於**：Intel / NVIDIA

**問題**：
IPMI 的 KCS 和 BT Interface 有什麼差異？什麼情況下用哪個？

**標準答案**：
```
KCS (Keyboard Controller Style)：
- 使用 I/O Port 通訊（如 0xCA2）
- 逐 byte 傳輸，需要等待 IBF/OBF 狀態
- 簡單但較慢
- 適合舊系統或簡單需求

BT (Block Transfer)：
- 也使用 I/O Port（如 0xE4）
- 可批次傳輸整個 message
- BMC 和 Host 各有 256-byte buffer
- 支援中斷驅動
- 較快，適合高負載場景

選擇考量：
- 大多數現代系統偏好 BT（若支援）
- KCS 相容性最好，所有 BMC 都支援
- AST2600 兩者都支援
```

### Q2：IPMI SDR 的用途是什麼？

**難度**：⭐⭐⭐
**常見於**：普遍

**問題**：
什麼是 SDR (Sensor Data Record)？它在 IPMI 架構中的角色？

**標準答案**：
SDR 是 IPMI 中描述感測器的資料結構。

主要用途：
1. 定義感測器的識別資訊
   - Sensor Number、Sensor Type、Entity ID

2. 定義讀數轉換
   - y = (M * x + B) * 10^K
   - M, B, K 儲存在 SDR 中

3. 定義閾值
   - Upper Critical, Upper Non-Critical
   - Lower Critical, Lower Non-Critical

4. 定義名稱
   - 人類可讀的 Sensor 名稱

SDR Repository：
- 儲存所有 SDR 的資料庫
- 開機時由 BMC 建立
- 可透過 IPMI 命令讀取（NetFn=0x0A, CMD=0x23）

| **熱插拔偵測** | 困難 | 原生支援 |
| **擴展性** | OEM 依賴 | 標準化擴展 |
|

### Q9-1：AST2600 Secure Boot Chain (原 Q9)

**難度**：⭐⭐⭐⭐⭐
**常見於**：AMD / NVIDIA

**問題**：
描述 AST2600 的 Secure Boot 啟動鏈。

**標準答案**：
AST2600 Secure Boot Chain：

1. Boot ROM (不可修改)
   - 位於 AST2600 晶片內部 ROM
   - 讀取 OTP 中的 Public Key Hash
   - 驗證 SPL 簽章
   - 失敗則停止啟動

2. SPL (Secondary Program Loader)
   - 位於 SPI Flash 開頭
   - 初始化 DDR4 記憶體
   - 驗證 U-Boot 簽章
   - 跳轉到 U-Boot

3. U-Boot
   - 初始化周邊設備
   - 載入並驗證 FIT Image
   - FIT 包含 Kernel + DTB + Initramfs

4. Linux Kernel
   - 正常啟動 Linux
   - 可選：使用 dm-verity 驗證 rootfs

金鑰管理：
- OTP 儲存 Public Key Hash（64 bytes SHA-512）
- 只能寫入一次，無法修改
- Private Key 由廠商安全保管

驗證演算法：
- RSA-2048 或 RSA-4096
- SHA-256 或 SHA-512

失敗處理：
- 啟動停止，無法進入系統
- Recovery 需要 UART 模式

### Q9-2：OpenBMC 的 Boot Sequence (啟動流程) 與 Flash Image 結構

**難度**：⭐⭐⭐⭐⭐
**常見於**：底層驅動 / System BSP 面試

**問題**：
請描述 OpenBMC 從過電到進入 Linux Shell 的完整啟動流程？
一個標準的 Flash 分區 (Partition Layout) 長什麼樣子？為什麼修改 `/usr` 的檔案重開機就不見了？

**標準答案**：
1. 啟動流程 (The Boot Stack)
   正確順序是：ROM → SPL → U-Boot → Kernel → Rootfs (Systemd)

   1.  **Boot ROM (SoC 內部)**
       *   這是晶片出廠時燒死的，無法更改。
       *   負責最基礎的硬體初始化 (SRAM)，從 SPI Flash 讀取 SPL 到 SRAM。

   2.  **SPL (Secondary Program Loader)**
       *   因為 SRAM 很小 (例如只有 64KB)，放不下完整的 U-Boot。
       *   SPL 的唯一任務：初始 DRAM，然後把完整的 U-Boot 載入到 DRAM。

   3.  **U-Boot (Bootloader)**
       *   這是功能最強大的 Bootloader。
       *   初始化更多周邊 (Network, MMC, USB)。
       *   從 SPI Flash 讀取 Kernel Image (通常是 FIT Image) 到 DRAM。
       *   根據 Boot Arguments (包含 DTB 位址) 跳轉到 Kernel。

   4.  **Linux Kernel**
       *   初始化所有驅動程式 (Drivers)。
       *   掛載 Root Filesystem (Rootfs)。
       *   執行第一個 Process：`/sbin/init` (即 Systemd)。

   5.  **Systemd (Userspace)**
       *   啟動 OpenBMC 相關服務 (xyz.openbmc_project...)。

2. SPI Flash Layout (典型 64MB 配置)
   這是一個由低位址到高位址的線性映射：

| Address | Partition Name | Description |
| :--- | :--- | :--- |
| **0x00000000** | `u-boot` | Bootloader (SPL + U-Boot) |
| **0x06000000** | `u-boot-env` | U-Boot 環境變數 (bootargs, bootcmd) |
| **0x00080000** | `kernel` | FIT Image (Kernel + DTB + Initramfs) |
| **0x00600000** | `rofs` | Read-Only Rootfs (SquashFS) -> `/usr`, `/bin` |
| **0x03000000** | `rwfs` | Read-Write Config (JFFS2/Overlay) -> `/etc`, `/var` |

   - **u-boot**：負責硬體初始化，載入 Kernel。
   - **kernel**：核心本體 (FIT Image)。
   - **rofs (Read-Only)**：放 OS 的二進位檔 (`ls`, `systemd`, `pldmd`)。為了壓縮率 (SquashFS) 和穩定性，這裡是**唯讀**的。
   - **rwfs (Read-Write)**：放使用者的設定檔 (`network-config`, `sensor-config`)。

3. OverlayFS：為什麼有些檔案會消失？
   OpenBMC 使用 OverlayFS 技術將 `rofs` (Lower Dir) 和 `rwfs` (Upper Dir) 合併起來給你看。

   - **當你修 /usr/bin/hello (在 rofs)**：
     - 因為 `rofs` 是唯讀的，你其實是寫不進去 Flash 的。你看到的修改只是暫存在 RAM (tmpfs) 裡，**斷電就沒了**。
   - **當你修 /etc/systemd/network/eth0 (在 rwfs)**：
     - `rwfs` 設有 Overlay 的 Upper Layer，你的修改會被真正寫入 SPI Flash 的 `rwfs` 分區。**斷電重開機還在**。

### Q9-3：為什麼需要 Device Tree (DTS)？

**難度**：⭐⭐⭐⭐
**常見於**：所有 Embedded Linux 面試

**問題**：
在 Device Tree 出現之前 (Legacy Linux)，我們是怎麼描述硬體的？DTS 帶來了什麼改善？Kernel 跟 DTS 的關係是什麼？

**標準答案**：
1. 解決的核心問題：Hardcoding (寫死在 Code 裡)
   - 在舊版 ARM Linux (pre-3.x)，硬體資訊是寫死在 C 語言裡的 (如 board-file)。
   - 每換一張板子，即使 CPU 一樣，只因為 I2C 地址不同，就要改 C code 重編 Kernel。
   - 這導致 /arch/arm/ 下充斥著數千個垃圾 board file。

2. Device Tree 的改善：
   - **分離策略**：將「硬體描述 (Data)」從「驅動程式 (Code)」中抽離。
   - **統一標準**：用一種標準的文字格式 (.dts) 描述硬體結構。
   - **通用性**：同一份 Kernel Binary (uImage)，只要搭配不同的 .dtb (Device Tree Blob)，就能在不同的板子上開機。

3. 形象化比喻 (重要面試技巧)：
   
   > **比喻：Kernel 是「遊戲主機 (Switch)」，Device Tree 是「遊戲卡帶 (Cartridge)」**
   > 
   > - **Legacy Linux (舊時代)**
   >   - 遊戲是**焊死**在主機板上的 (Hardcoded)。
   >   - 想換遊戲玩？抱歉，你要把整台主機拆掉，重新焊接 (Recompile Kernel)。
   >
   > - **Modern Linux (Device Tree)**
   >   - 主機 (Kernel) 變成通用的，它只負責運算和顯示。
   >   - 遊戲內容 (硬體描述) 存在卡帶 (.dtb) 裡。
   >   - 想換遊戲玩？**換張卡帶 (.dtb) 就好，主機不用換 (不用重編 Kernel)！**

4. 開機流程中的 DTS：
   U-Boot 會先把 Kernel 載入記憶體，再把 DTB 載入記憶體，然後告訴 Kernel：「嘿，卡帶在記憶體位址 0x50000000，照著上面的說明去玩吧！」。

### Q9-4：FIT Image 結構解密：它到底包了什麼？

**難度**：⭐⭐⭐⭐
**常見於**：U-Boot / Yocto 相關面試

**問題**：
FIT Image (`image.itb`) 裡面包含哪些東西？有包含 U-Boot 嗎？如果不開 Secure Boot，我可以單獨換 DTB 嗎？

**標準答案**：
1. FIT Image (Flattened Image Tree) 結構剖析
   它就像一個壓平的資料夾 (Container)，裡面通常只包含三樣東西：
   - **Kernel Image** (`zImage` 或 `Image`)
   - **Device Tree Blobs** (`.dtb`) - 可能有多個，對應不同板子
   - **Initramfs** (Optional) - 極小的 Ramdisk，用於載入必要驅動

   **❌ 絕對不包含：**
   - **SPL / U-Boot**：它們住在 SPI Flash 較前段的獨立分區 (`u-boot` partition)。
   - **Systemd / Rootfs**：真正的作業系統檔案系統住在後面超大的獨立分區 (`rofs` partition，通常是 SquashFS)。

2. 非 Secure Boot 場景：可以單獨換 DTB 嗎？
   **⭕ 答案：當然可以！而且這是 RD 的日常 (U-Boot 指令大法)。**

   **💡 方法比較 (Execution Context)**
   | 方法 | 執行位置 | 狀態 | 效力 | 需要 Reboot? |
   | :--- | :--- | :--- | :--- | :--- |
   | **方法 A (RD 開發用)** | U-Boot Console (RAM) | **暫時性** (重開機消失) | 免燒錄 | 否 (直接 `bootz`) |
   | **方法 B (使用者更新)** | Linux Shell (Flash) | **永久性** (寫入 Flash) | 需燒錄 | **是** (必須 reboot) |

   > **方法 A 範例 (RD最愛)**：
   > ```bash
   > tftp 0x81000000 Image       # 下載 Kernel
   > tftp 0x82000000 board.dtb   # 下載 DTB (換這裡就好！)
   > bootz 0x81000000 - 0x82000000
   > ```

### Q9-5：Secure Boot 深度解析：簽章與 Chain of Trust

**難度**：⭐⭐⭐⭐⭐
**常見於**：AMD / NVIDIA / Server ODM

**問題**：
什麼是「數位簽章」？OpenBMC 的 Chain of Trust 是如何建立的？如果我偷偷換了 Device Tree (DTB) 會發生什麼事？

**標準答案**：
1. 什麼是數位簽章 (Digital Signature)？
   - **原理**：Hash (SHA-256) + 非對稱加密 (RSA/ECDSA)。
   - **流程**：原廠用**私鑰**對 Image 的 Hash 加密；設備端用**公鑰**解密驗證 Hash。

2. Chain of Trust (信任鏈)
   每一層都在執行下一層之前先驗證它：
   - **Root of Trust (RoT)**：SoC 內部的 Boot ROM + OTP 公鑰 (最源頭，絕對信任)。
   - **Step 1**：ROM 驗證 SPL 的簽章 → 通過才執行 SPL。
   - **Step 2**：SPL 驗證 U-Boot 的簽章 → 通過才執行 U-Boot。
   - **Step 3**：U-Boot 驗證 Kernel (FIT Image) 的簽章 → 通過才執行 Kernel。

3. Device Tree 可以被單獨置換嗎？
   - **答案**：如果開啟了 Secure Boot，**不行！**
   - **原因**：
     - 在 FIT Image 架構中，DTB 是被打包在 image.itb 裡面的。
     - 簽章是對 **整個 image.itb** (包含 Kernel + DTB) 進行的。
     - 只要你偷改了 DTB 的任何一個 byte，整個 image 的 **Hash 值就會改變**。
   - **後果**：
     - U-Boot 驗證時發現 Hash 不符 (Signature Verification Failed)。
     - U-Boot 拒絕啟動 Kernel，防止駭客透過 DTB 注入惡意驅動。

### Q9-6：觀念統整：既然 Kernel 通用，為何 FIT Image 又要打包在一起？

**難度**：⭐⭐⭐⭐⭐
**常見於**：高階系統架構面試

**問題**：
Q9-3 (原 Q10-2) 說 DTS 讓 Kernel 變通用；但 Q9-5 (原 Q10-4) 又說 FIT Image 把大家打包在一起不能換。這不是矛盾嗎？

**標準答案**：
這不矛盾，因為這是**兩個不同階段**的議題：

1. **Build Time / Development Phase (RD 的快樂)**
   - **視角**：開發者。
   - **痛點解決**：Kernel 編一次就好 (Universal Binary)，隨意搭配不同 DTB 測試。
   - **手段**：使用 Q9-4 (原 Q10-3) 的「方法 A (RAM 載入)」。

2. **Runtime / Deployment Phase (User 的限制)**

   - **安全考量**：產品出廠時，為了防止亂改硬體定義或惡意攻擊。
   - **手段**：使用 Secure Boot，把 Universal Kernel 和 Specific DTB 打包簽章成 FIT Image。
   - **結果**：技術上 Kernel 是通用的，但為了安全，被強制綁定。

**一句話總結**：
「DTS 的通用性是為了**方便 RD 開發與維護**；FIT Image 的打包與簽章是為了**確保出廠後的產品安全**。」

### Q11：MCTP over PCIe VDM

**難度**：⭐⭐⭐⭐⭐
**常見於**：NVIDIA / AMD

**問題**：
解釋 MCTP over PCIe VDM 的運作方式。

**標準答案**：
MCTP over PCIe VDM (Vendor Defined Message)：

PCIe VDM 是 PCIe 規範中定義的廠商擴展機制。
DMTF 定義了如何在 VDM 中傳輸 MCTP 封包。

封包結構：
```
┌──────────────────────────────────────────┐
│  PCIe TLP Header                          │
│  - Type: Message (TLP Type 0x10)         │
│  - Message Code: Vendor Defined (0x7F)   │
├──────────────────────────────────────────┤
│  VDM Header                               │
│  - Vendor ID: 0x1AB4 (DMTF)              │
│  - PCIe Target ID                        │
├──────────────────────────────────────────┤
│  MCTP Header                              │
│  - Dest/Src EID                          │
│  - Message Tag                           │
├──────────────────────────────────────────┤
│  MCTP Payload (PLDM Message)              │
└──────────────────────────────────────────┘
```

優點（相比 SMBus）：
- 頻寬更高（PCIe vs 100kHz I2C）
- 延遲更低
- 更可靠（PCIe 有 CRC 和重傳）

- 可接收 Host 的 VDM
- 用於 PLDM/SPDM 通訊

### Q14：Redfish EventService SSE vs Webhook

**難度**：⭐⭐⭐⭐
**常見於**：Google / Meta

**問題**：
比較 Redfish EventService 的 SSE 和 Webhook 機制。

**標準答案**：
| | SSE | Webhook |
| :--- | :--- | :--- |
| **連線方式** | Client 開啟長連線 | BMC 主動 POST |
| **即時性** | 毫秒級 | 可能有延遲 |
| **網路配置** | Client 需連入 BMC | BMC 需連出 |
| **NAT 友善度** | 良好 | 可能有問題 |
| **失敗處理** | 自動重連 | 需重試邏輯 |
| **效能** | 較好（無連線建立） | 每事件一次 HTTP |
| **複雜度** | Client 需處理 SSE | Server 端簡單 |

SSE 適用：
- 即時監控面板
- 低延遲需求

Webhook 適用：
- 雲端整合
- 事件處理系統
- 無法維持長連接的環境

OpenBMC 實作：
- bmcweb 支援兩種
- SSE 用 Boost.Beast 實作
- Webhook 用 libcurl POST

### Q15：D-Bus PropertyChanged Signal 如何訂閱？

**難度**：⭐⭐⭐⭐
**常見於**：Google / Intel

**答案**：
```cpp
// C++ 訂閱範例
#include <sdbusplus/bus.hpp>
#include <sdbusplus/bus/match.hpp>

int main()
{
    auto bus = sdbusplus::bus::new_default();
    
    auto match = sdbusplus::bus::match::match(
        bus,
        sdbusplus::bus::match::rules::propertiesChanged(
            "/xyz/openbmc_project/sensors/temperature/CPU0_Temp",
            "xyz.openbmc_project.Sensor.Value"),
        [](sdbusplus::message::message& msg) {
            std::string interface;
            std::map<std::string, std::variant<double>> props;
            msg.read(interface, props);
            
            if (auto it = props.find("Value"); it != props.end())
            {
                double value = std::get<double>(it->second);
                std::cout << "New value: " << value << std::endl;
            }
        });
    
    while (true)
    {
        bus.process_discard();
        bus.wait();
    }
}

// busctl 測試
busctl monitor xyz.openbmc_project.HwmonTempSensor
```

### Q16：深入教學 SPDM (Security Protocol and Data Model)

**難度**：⭐⭐⭐⭐⭐
**常見於**：NVIDIA / AMD / Server Security Team

**問題**：
我完全不懂 SPDM，請從頭教我：它是做什麼的？如何運作？什麼是 Measurement？

**標準答案**：
1.  **SPDM 是什麼？**
    *   **全名**：Security Protocol and Data Model (DMTF 標準)。
    *   **一句話解釋**：它是「硬體元件的身分證查驗與健康檢查協定」。
    *   **原本**：MCTP 只能傳輸資料 (PLDM/NVMe-MI)，不知道對方是誰。
    *   **現在**：在傳資料前，先用 SPDM 確認「你是真的 NVIDIA GPU 嗎？」且「你的韌體有沒有被駭客竄改？」。

2.  **運作流程 (The SPDM Handshake)**
    BMC (Requester) 與 Device (Responder) 的對話流程：

    1.  **VDO (Vendor Defined Object) - 選用**
        *   確認對方是不是我要找的供應商設備。

    2.  **GET_VERSION (版本協商)**
        *   BMC: "我懂 SPDM 1.0 和 1.1。"
        *   Device: "那我們用 1.1 溝通吧。"

    3.  **GET_CAPABILITIES (能力確認)**
        *   BMC: "你會加密嗎？你會簽章嗎？"
        *   Device: "我會 RSA-4096 簽章，也會 AES-256 加密。"

    4.  **NEGOTIATE_ALGORITHMS (演算法協商)**
        *   雙方約定好接下來用哪個 Hash (SHA-384) 和 Signature (ECDSA) 演算法。

    5.  **GET_DIGESTS / GET_CERTIFICATE (憑證交換) - 身分查驗 (Who are you?)**
        *   BMC: "請把你的身分證 (Certificate Chain) 拿出來。"
        *   Device: 回傳 X.509 憑證鏈 (Root CA -> Intermediate CA -> Device Cert)。
        *   BMC 驗證：去查 Root CA 是否在信任清單中。驗證通過 = 這是真品。

    6.  **CHALLENGE / RESPONSE (挑戰應答) - 活體檢測 (Are you alive?)**
        *   BMC: "這是一個隨機數 (Nonce)，請用你的私鑰簽名傳回來。"
        *   Device: 用私鑰簽章 (Nonce)。
        *   BMC: 用公鑰解開驗證。
        *   **目的**：防止重放攻擊 (Replay Attack)，證明對方真的持有私鑰。

    7.  **GET_MEASUREMENTS (韌體測量) - 健康檢查 (Are you healthy?)**
        *   BMC: "請回報你目前 Firmware 的 Hash 值 (Measurement)。"
        *   Device: 回傳各階段韌體 block 的 Hash (Signed)。
        *   BMC: 拿這個 Hash 去跟「黃金標準 (Reference Manifest/RIM)」比對。
        *   **結果**：如果 Hash 不符，代表韌體被駭客植入後門，BMC 拒絕使用此卡。

3.  **為什麼需要 SPDM？ (CMA / DICE)**
    *   **CMA (Component Measurement and Authentication)**：確保伺服器上的每一張卡 (網卡、RAID卡、GPU) 都是可信的。
    *   **供應鏈安全**：防止工廠內鬼偷換假貨，或運送途中被刷入惡意韌體。
