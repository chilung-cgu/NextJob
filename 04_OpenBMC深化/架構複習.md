## 🏗️ Chapter 1: 核心架構觀念

### 1.1 什麼是 BMC？ (The Definition)
BMC (Baseboard Management Controller) 是伺服器主機板上的一個 **獨立嵌入式系統** (System on Chip)。
它的電源來自 **Standby Power (V_Aux)**，這意味著：**即使伺服器主電源關閉 (Power Off) 或作業系統當機 (Kernel Panic)，BMC 仍然活著。**

這賦予了它神聖的職責：**Out-of-band Management (帶外管理)**。

#### 🧠 心智模型：大樓管理員
想像伺服器是一棟豪宅 (Host System)，裡面住著主人 (OS/CPU)。
BMC 就是住在門房的 **管理員 (Janitor)**：
- **獨立運作**：管理員有自己的房間和電源，不受主人是否睡覺影響。
- **監控環境**：管理員盯著溫度、濕度 (Sensor)，有火災 (Over-temperature) 立刻報警。
- **遠端控制**：屋主忘記帶鑰匙，打電話給管理員幫忙開門 (Remote Power Control)。
- **維護通道**：水電工 (System Admin) 來修水管時，是通過管理員進入，而不是打破窗戶。

---

### 1.2 OpenBMC 四層架構 (The 4-Layer Model)
OpenBMC 的設計非常模組化，我們可以將其剖析為標準的四層結構。
**這個模型將貫穿整份教科書，請牢記。**

```mermaid
graph TD
    user((User / Admin)) --> L4
    
    subgraph L4 [Layer 4: Management Interfaces]
        Redfish[Redfish API]
        IPMI[IPMI / KCS]
        WebUI[Web UI]
        SSH[SSH Console]
    end

    L4 --> L3
    
    subgraph L3 [Layer 3: The Nervous System (System Bus)]
        DBus[D-Bus (Binder)]
        Mapper[Phosphor Mapper]
        ObjectMapper[Object Manager]
    end

    L3 --> L2
    
    subgraph L2 [Layer 2: Services & Logic (Userspace)]
        FanCtrl[Phosphor Fan Control]
        SensorSvc[Hwmon / Dbus-Sensors]
        StateMgr[State Manager]
        Logger[Phosphor Logging]
    end

    L2 --> L1
    
    subgraph L1 [Layer 1: Kernel & Hardware (The Foundation)]
        Kernel[Linux Kernel 5.x/6.x]
        Drivers[Hwmon / I2C / GPIO Drivers]
        SoC[ASPEED SoC (AST2500/2600)]
        HW[Physical Sensors / VR / LEDs]
    end
```

#### Layer 1: 基礎設施層 (Kernel & Hardware)
這是地基。包含 ASPEED SoC 晶片、Linux Kernel 以及底層驅動程式。
- **職責**：將物理世界的電壓訊號 (I2C, GPIO) 轉換為軟體可讀的檔案介面 (sysfs)。
- **關鍵字**：Device Tree (DTS), Hwmon, I2C subsys.

#### Layer 2: 服務邏輯層 (Services)
這是大腦皮層。負責實際的業務邏輯。
- **職責**：讀取數值、判斷邏輯（如：溫度 > 50度則風扇轉速 + 10%）。
- **關鍵字**：`phosphor-hwmon`, `dbus-sensors`, `phosphor-state-manager`.

#### Layer 3: 神經網路層 (D-Bus)
這是血管與神經。OpenBMC 的靈魂。
- **職責**：讓 Layer 2 的各個獨立服務能夠互相溝通，而不需要知道對方的存在 (Decoupling)。
- **關鍵字**：`sdbusplus`, `busctl`, `xyz.openbmc_project`.

#### Layer 4: 對外介面層 (Interfaces)
這是櫃台。負責接待外部的使用者。
- **職責**：將內部的 D-Bus 資料轉換為使用者看得懂的格式 (JSON/HTML)。
- **關鍵字**：`bmcweb` (Redfish), `phosphor-ipmi-host`, `nginx`.

 ## 🧠 Chapter 2: 神經網路層 (D-Bus Deep Dive)

### 2.1 為什麼需要 D-Bus？ (The Nervous System)
在 OpenBMC 中，D-Bus 不僅僅是一個 IPC (Inter-Process Communication) 機制，它是整個系統的 **"骨幹"**。
所有的 Daemon (如 Fan Control, Sensor Monitoring, Web Server) 都是獨立的 Process，它們互不認識，唯一的溝通方式就是 **D-Bus**。

- **解耦合 (Decoupling)**：`phosphor-hwmon` 只負責讀溫度並丟上 D-Bus，它根本不在乎是誰要讀這個溫度 (可能是 WebUI，也可能是 Fan Control)。
- **語言無關 (Language Agnostic)**：你可以用 C++, Python, Go 寫任何 Service，只要大家講 D-Bus 協定就能通。

---

### 2.2 D-Bus 的四維座標 (Addressing Model)
要準確找到一個 D-Bus 資源，你需要四個座標。這在面試時非常容易被問倒，請務必搞懂。

| 座標層級 | 比喻 (地址) | OpenBMC 範例 |
| :--- | :--- | :--- |
| **0. Bus** | 哪個城市 | `System Bus` (通常只有這一個) |
| **1. Service** | 哪棟大樓 (Process) | `xyz.openbmc_project.Hwmon-10512` |
| **2. Object Path** | 哪個房間 (URL) | `/xyz/openbmc_project/sensors/temperature/cpu0` |
| **3. Interface** | 哪種規格的插座 | `xyz.openbmc_project.Sensor.Value` |
| **4. Property/Method** | 插座上的電壓 | `Value` (Property), `Unit` (Property) |

> **💡 面試口訣**：
> "Service 是 Process，Object 是資源，Interface 是功能定義，Property 是數值。"

---

### 2.3 服務發現機制 (The Mapper)
面試官問：「Redfish 怎麼知道 CPU 溫度是由哪個 Service 提供的？」
答案：**Object Mapper (`xyz.openbmc_project.ObjectMapper`)**。

它是 OpenBMC 的 **"電話簿" (Yellow Pages)**。
1. 當 `phosphor-hwmon` 啟動時，會告訴 Mapper：「我有 `/sensors/temp/cpu0` 這個物件」。
2. 當 `bmcweb` 想讀 CPU 溫度時，它會先問 Mapper：「誰擁有 `/sensors/temp/cpu0`？」。
3. Mapper 回答：「是 `xyz.openbmc_project.Hwmon-10512`」。
4. `bmcweb` 再去跟該 Service 要資料。

---

### 2.4 D-Bus 實戰指令 (The Toolbox)
熟悉 `busctl` 指令是 OpenBMC 工程師的基本功。

#### 1. 列出所有部門 (List Services)
```bash
busctl list
# 看到一堆 xyz.openbmc_project... 就是成功了
```

#### 2. 及其管理的所有物件 (Tree)
```bash
busctl tree xyz.openbmc_project.HwmonTempSensor
# 顯示：
# └─/xyz/openbmc_project/sensors
#   └─/xyz/openbmc_project/sensors/temperature/cpu0
```

#### 3. 查看詳細資料 (Introspect) - 最常用！
```bash
busctl introspect \
  xyz.openbmc_project.HwmonTempSensor \
  /xyz/openbmc_project/sensors/temperature/cpu0
```

#### 4. 讀取數值 (Get Property)
```bash
busctl get-property \
  xyz.openbmc_project.HwmonTempSensor \
  /xyz/openbmc_project/sensors/temperature/cpu0 \
  xyz.openbmc_project.Sensor.Value \
  Value
# 回傳: d 45.123 (double, 45度)
```

#### 5. 監控訊息 (Monitor) - Debug 神器
```bash
busctl monitor xyz.openbmc_project.HwmonTempSensor
# 像 Wireshark 一樣，即時看 D-Bus 流量
```

### 2.5 API 定義檔 (phosphor-dbus-interfaces)
所有的 Interface (如 `xyz.openbmc_project.Sensor.Value`) 都是在 `phosphor-dbus-interfaces` repo 中定義的 YAML 檔。
這相當於 API 的 **"合約" (Contract)**。

```yaml
# Sensor/Value.interface.yaml
description: >
    A simple sensor value.
properties:
    - name: Value
      type: double
      description: The reading of the sensor.
    - name: Unit
      type: enum[...]
      description: The unit of the reading.
```

### 3. phosphor-hwmon

負責讀取硬體感測器數值。

運作方式：
1. 讀取 Linux hwmon sysfs (/sys/class/hwmon)
2. 將數值透過 D-Bus 發布
3. 提供 Sensor.Value 介面

設定檔位置：
`/etc/default/obmc/hwmon/`

設定檔範例：
```properties
# 48-0048.conf (I2C device at address 0x48)
LABEL_temp1=cpu0_temp
LABEL_temp2=cpu1_temp
```

## ⚙️ Chapter 3: 現代硬體管理 (Entity-Manager)

> **這是 Meta / Intel 平台的精隨。**
> 相比於傳統 IBM 風格的 `phosphor-inventory-manager` (靜態 YAML)，`entity-manager` 是動態的、靈活的 JSON 設定。

### 3.1 為什麼需要 Entity-Manager？
傳統 BMC 韌體 (如 IBM Power) 在編譯時就把所有 Sensor 寫死了 (Static Layout)。
但在現代 Hyperscale 資料中心 (如 Meta Yosemite 4)，伺服器是 **模組化** 的：
- Slot 1 可能插運算卡
- Slot 2 可能插加速卡
- Slot 3 可能是空的

**我們不能為每一種排列組合編譯一個韌體。**
我們需要一個能 **"動態探測 (Probe)"** 硬體並載入對應設定的機制，這就是 `entity-manager`。

---

### 3.2 運作原理 (The Probe Loop)
`entity-manager` 的核心是一個無窮迴圈的探測機制：

1.  **讀取設定**：啟動時讀取 `/usr/share/entity-manager/configurations/*.json`。
2.  **執行探測 (Probe)**：對照 JSON 裡的 `"Probe"` 條件 (通常是 I2C 偵測)。
    - 例如：「I2C Bus 2, Address 0x48 有沒有回應？」
3.  **載入模型 (Load)**：
    - 如果 Probe 成功 (MATCH)，將該 JSON 定義的 `"Exposes"` (Sensor, Fan, Pid) 發布到 D-Bus。
    - 如果 Probe 失敗，則忽略該設定。
4.  **動態監控**：它會監控 `InterfacesAdded` 信號，如果有人插拔硬體 (Hot-plug)，它會重新執行 Probe。

---

### 3.3 JSON 設定檔詳解 (The Config)
這是你工作中最常要改的檔案。

```json
{
    "Name": "Yosemite 4 Fan Board",
    "Probe": "xyz.openbmc_project.FruDevice({'PRODUCT_NAME': 'Fan Board*'})",
    "Exposes": [
        {
            "Name": "Fan 0",
            "Type": "AspeedFan",
            "Connector": {
                "Pwm": 0,
                "Tachs": [0]
            }
        },
        {
            "Name": "Outlet Temp",
            "Type": "TMP75",
            "Bus": 12,
            "Address": "0x49"
        }
    ]
}
```

- **Probe**: 觸發條件。這裡指「當 FRU Device 的 PRODUCT_NAME 包含 'Fan Board' 時」。
- **Exposes**: 這個板子上有什麼東西。
    - `Type`: 告訴 `dbus-sensors` 用什麼驅動 (AspeedFan, TMP75, ADM1278)。
    - `Bus/Address`: 硬體位置。

### 3.4 下游服務的連動 (The Observer)
`entity-manager` 自己不讀 Sensor，它只負責 **"宣告"**。
真正讀 Sensor 的是 `dbus-sensors` (如 `psusensor`, `fansensor`)。

1. `entity-manager` 在 D-Bus 上宣告：「這裡有一個 TMP75 @ Bus 12, Addr 0x49」。
2. `dbus-sensors` (hwmontempsensor) 看到這個宣告。
3. `dbus-sensors` 負責去 Kernel `sysfs` 讀取數值，並發布 `Sensor.Value`。

> **💡 教科書重點**：這就是 **Configuration (Entity-Manager)** 與 **Execution (Sensors)** 的分離設計。

---

### 3.5 實戰 Debug (Troubleshooting)

**情境：我加了 JSON，但 Sensor 沒出現？**

1. **檢查 Probe 是否成功**
   ```bash
   busctl tree xyz.openbmc_project.EntityManager
   # 如果你的板子沒出現在列表裡，就是 Probe 條件沒過。
   ```

2. **檢查 FRU 資料**
   ```bash
   busctl introspect xyz.openbmc_project.FruDevice \
     /xyz/openbmc_project/FruDevice/i2c_2_50
   # 確認讀到的 PRODUCT_NAME 跟你的 JSON Probe 條件是否一致。
   ```

3. **檢查語法錯誤**
   ```bash
   journalctl -u xyz.openbmc_project.EntityManager | grep error
   # JSON 格式錯誤是常見原因 (多一個逗號之類)。
   ```

## 🔌 Chapter 4: 管理介面 (Management Interfaces)

> **"櫃台"層級的互動。**
> 詳細的面試應答策略與 API 範例，請務必參閱 `面試重點.md` (Exam Prep)。

### 4.1 Redfish (現代標準)
- **核心比喻**：瀏覽網頁。RESTful API，Human Readable (JSON)。
- **傳輸層**：HTTPS (Port 443)。
- **核心結構**：Systems (邏輯), Chassis (物理), Managers (BMC本身)。
- **關鍵操作**：`GET` (讀 Sensor), `POST` (Action, 如 Reset), `PATCH` (設定屬性)。

### 4.2 IPMI (Legacy 標準)
- **核心比喻**：發電報。Binary 格式，難讀，但在舊系統仍廣泛使用。
- **傳輸層**：UDP (Port 623), KCS, BT。
- **關鍵限制**：安全性較弱 (Cipher 0 漏洞)，描述能力有限 (SDR)。

### 5.2 如何撰寫 Recipe？(Recipe 101)
這是 OpenBMC 開發者的日常。面試常問：「如何新增一個 Hello World 服務？」

```makefile
# example_1.0.bb
SUMMARY = "My Example Service"
LICENSE = "Apache-2.0"

# 1. 原始碼哪裡來？
SRC_URI = "git://github.com/my/repo.git;branch=main"
SRCREV = "${AUTOREV}"

# 2. 依賴什麼？

RDEPENDS:${PN} = "libsystemd"

# 3. 繼承什麼類別？(CMake? Meson? Systemd?)
inherit cmake systemd

# 4. 安裝什麼檔案？
SYSTEMD_SERVICE:${PN} = "example.service"
```

### 5.3 高效開發流程 (Devtool Workflow)
面試官不想聽到「我都改完 code 再重新 bitbake image」，那太慢了。
**標準答案**：使用 `devtool`。

1.  **Modify**: `devtool modify phosphor-hwmon` (拉取 source code 到 workspace)。
2.  **Edit**: 在 `build/workspace/sources/phosphor-hwmon` 修改 C++ 程式碼。
3.  **Build**: `devtool build phosphor-hwmon` (只編譯這個套件，超快)。
4.  **Deploy**: `devtool deploy-target phosphor-hwmon root@bmc-ip` (推送到實機測試)。
5.  **Run**: 在 BMC 上重啟服務驗證。
6.  **Update**: `devtool finish phosphor-hwmon meta-my-layer` (將修改轉成 patch)。

## 📡 Chapter 6: 進階通訊協定 (PLDM & SPDM)
> 這是區分 "Junior" 與 "Senior" 的關鍵領域。

### 6.1 PLDM (Platform Level Data Model)
IPMI 的繼任者，專門處理 BMC 與「擴充卡」(GPU, NIC) 之間的溝通。

#### 核心傳輸層 (MCTP)
MCTP (Management Component Transport Protocol) 是 PLDM 的載體。
- 它可以跑在 **SMBus/I2C** (低速，接 GPU)。
- 也可以跑在 **PCIe VDM** (高速，接 Host CPU)。

#### Type 分類 (The Types)
PLDM 不是像 IPMI 那樣一團混亂，它有嚴格的 Type 定義：
- **Type 2 (Monitoring)**: 讀溫度、電壓 (PDR, Sensor Reading)。
- **Type 5 (Firmware Update)**: 幫擴充卡更新韌體。

### 6.2 SPDM (Security Protocol)
供應鏈安全的守門員。
- **身份驗證 (Authentication)**：BMC 問擴充卡：「你是原廠的嗎？」(Challenge-Response)。
- **完整性量測 (Measurement)**：BMC 問擴充卡：「你的韌體有沒有被改過？」(Get Measurements)。
- 這是 **Zero Trust** 架構的基礎。

## 🧠 Chapter 7: 硬體深潛 (Hardware Deep Dive)

### 7.1 AST2600 SoC 規格解析
目前市場主流 (2023-2025)。
- **CPU**: Dual Core ARM Cortex-A7 (1.2GHz)。
- **RAM**: DDR4 (重要！比 AST2500 的 DDR3 快很多)。
- **Security**: **Hardware Root of Trust** (這是重點，支援 Secure Boot)。

### 7.2 GPIO 控制實戰
雖然我們通常用 D-Bus 控制 LED，但有時候 Debug 會直接打 GPIO。
**新舊方法都要會：**

1.  **Legacy (sysfs)**: `echo 128 > /sys/class/gpio/export` (已過時，Kernel 6.x 逐步廢棄)。
2.  **Modern (libgpiod)**:
    - `gpioinfo`: 查看所有 GPIO 狀態。
    - `gpioset gpiochip0 128=1`: 設定 High。
    - `gpioget gpiochip0 128`: 讀取值。

## 📚 Chapter 8: 工程師實戰場景 (Case Studies)

### Scenario 1: 大量 Sensor 的效能問題
**場景**：Yosemite 4 有 4 個 Slot，幾百個 Sensor，系統變慢。
**解決方案**：
- 放棄 `phosphor-hwmon` (Polling 機制太耗 CPU)。
- 改用 `dbus-sensors` (Event Driven + Async IO)。
- 調整 Polling Interval，非關鍵 Sensor 設長一點。

### Scenario 2: 處理「過熱但沒關機」的 Bug
**場景**：溫度超過 Critical，但 Host 沒關機。
**除錯流程**：
1.  **Check Sensor**: `busctl get-property` 確認數值真的超標了嗎？
2.  **Check Threshold**: `busctl introspect ... Threshold.Critical` 確認閥值設定對嗎？
3.  **Check Signal**: `busctl monitor` 有沒有看到 `PropertiesChanged` (AlarmHigh) 信號發出？
4.  **Check Action**: `phosphor-pid-control` 或 `host-state-manager` 有沒有訂閱這個信號？即這條神經有沒有接好？

### Scenario 3: Secure Boot 驗證失敗
**場景**：新編譯的 image 燒進去無法開機。
**除錯流程**：
1.  連接 UART Console。
2.  看 U-Boot log：`Verifying image... FAILED`。
3.  **Root Cause**: 你的 Private Key 跟燒在 OTP 裡的 Public Key Hash 不匹配。你要嘛用正式 Key 簽章，要嘛換一塊那是 Development Fuse 的板子。
