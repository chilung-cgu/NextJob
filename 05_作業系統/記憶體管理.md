# 💾 Linux 記憶體管理 (Memory Management)

> **學習目標**
> 1.  建立 **Virtual Memory** 的 Mental Model (MMU, TLB, Page Table)。
> 2.  深入 ARM64 **硬體機制** (4-level Page Table, ASID)。
> 3.  精通 **Kernel Allocators** (Buddy System, Slab/Slub) 與 `kmalloc`/`vmalloc` 差異。
> 4.  掌握 **Page Fault** 處理流程、**COW** 機制與 **OOM Killer** 行為。

---

## 📌 Context: 為什麼需要虛擬記憶體 (VM)？

如果程式直接操作實體記憶體 (Physical Memory)，會有三大災難：
1.  **安全性 (Security)**: Process A 可以隨意寫入 Process B 的資料，甚至覆蓋 Kernel。
2.  **碎片化 (Fragmentation)**: 記憶體中充滿了空隙，明明總量夠，卻放不下一個大陣列。
3.  **限制性 (Limitations)**: 你的程式不能大於實體 RAM (e.g., 在 4GB RAM 上跑 10GB 遊戲)。

**Virtual Memory** 解決了這一切：給每個 Process 一個「獨佔整台電腦」的幻覺，由 OS 和硬體 (MMU) 在背後偷偷做地址轉換。

## 🧠 Mental Model (核心觀念圖解)

### 1. 兩層視角 (The Mapping View)

```text
       Process View                  Hardware Reality
  (Virtual Address Space)             (Physical RAM)
┌───────────────────────┐         ┌───────────────────┐
│     0xCAFE_BABE       │ ──MMU──▶│    0x8000_1000    │
└───────────────────────┘         └───────────────────┘
```
MMU (Memory Management Unit) 是中間的翻譯官。它查表 (**Page Table**) 來決定 VA 對應到哪個 PA。

### 2. 快取加速 (TLB)

查 Page Table 很慢 (要讀寫 RAM 好幾次)。
**TLB (Translation Lookaside Buffer)** 是 "Page Table 的 Cache"。
CPU 先問 TLB，如果 Hit (命中) 就直接拿到 PA，如果 Miss 才去查表。

## 🔷 Logic I: 硬體機制 (MMU & Page Table)

### 1. ARM64 四級頁表 (4-level Page Table)

現代 ARM64 (4KB Page, 48-bit VA) 使用四層查表結構。

```text
VA [47:0] 分解:
┌────────┬────────┬────────┬────────┬────────────┐
│ 47:39  │ 38:30  │ 29:21  │ 20:12  │   11:0     │
│ L0 idx │ L1 idx │ L2 idx │ L3 idx │ Page Offset│
└────┬───┴────┬───┴────┬───┴────┬───┴──────┬─────┘
     │        │        │        │          │
     ▼        ▼        ▼        ▼          ▼
   [PGD] -> [PUD] -> [PMD] -> [PTE] -> Physical Page + Offset
```

-   **CR3 / TTBR**: 存放 L0 (PGD) 的實體位址。Context Switch 時就是切換這個暫存器。
-   **TTBR0_EL1**: User Space (低位址)。
-   **TTBR1_EL1**: Kernel Space (高位址)。

### 2. TLB 與 ASID

-   **問題**: 切換 Process (CR3 改變) 後，舊 Process 的 TLB Entry 就失效了，必須 Flush TLB。Flush 很貴！
-   **解法 (ASID)**: Address Space ID。
    -   TLB Entry = `VA | PA | ASID`
    -   Process A (ASID=1) 存取時，不會誤用到 Process B (ASID=2) 的並存 Entry。
    -   **結果**: Context Switch 不需要 Flush TLB (除非 ASID 用完輪替)。

## 🔷 Logic II: OS 軟體機制

### 1. Page Fault (分頁錯誤)

當 MMU 發現「查無此頁」或「權限錯誤」時，觸發 Exception，Kernel 接手處理：

1.  **Minor Fault**: Page 其實在 RAM 裡 (例如 mmap 的檔案已在 Page Cache)，只是 Page Table 沒建立。Kernel 建立 Mapping 即可，極快。
2.  **Major Fault**: Page 真的不在 RAM (在 Disk 或 Swap)。需要 Disk I/O，極慢。
3.  **Invalid Fault**: 真的存取非法位址 (SegFault)。Kernel 發送 `SIGSEGV` 殺掉 Process。

### 2. Copy-on-Write (COW)

`fork()` 的神技。父子 Process 分家時，**不複製實體記憶體**，只複製 Page Table，並將所有 Page 設為 **Read-Only**。
-   **讀取**: 大家共用同一個實體 Page。
-   **寫入**: 觸發 Page Fault (Permission Fault)。Kernel 發現是 COW Page，這才**複製**一份新的實體 Page 給寫入者，並改為 Read-Write。

### 3. Demand Paging (按需分頁)

`malloc(1GB)` 瞬間完成，因為 Kernel 只是這在你的 `mm_struct` 裡記上一筆 VMA (Virtual Memory Area)，**完全沒有分配實體 RAM**。
直到你真的去寫入某個位址，觸發 Page Fault，Kernel 才臨時分配一個 Page 給你。

## 🔷 Logic III: Kernel Allocators (核心配置器)

Kernel 內部如何管理自己的記憶體？

```text
High Level APIs (kmalloc, vmalloc)
       │
       ▼
   [Slab Allocator] (SLUB)  <-- 管理小物件 (task_struct, inode)
       │
       ▼
   [Buddy System] (Page Allocator) <-- 管理整頁 (4KB, 8KB...)
       │
       ▼
   [Physical RAM]
```

### 1. Buddy System (夥伴系統)
解決**外部碎片**。
-   管理 2^0 到 2^10 個 Pages 的區塊。
-   釋放時，檢查 "Buddy" (相鄰區塊) 是否空閒，是則合併。

### 2. Slab Allocator (SLUB)
解決**內部碎片** (Buddy System 最小單位 4KB，但我只要申請 32 bytes)。
-   從 Buddy 拿一個 Page，切成無數個 32-byte 小塊。
-   **kmalloc** 底層就是用 Slab (預建 8B, 16B, ..., 4096B 的 Cache)。

### 3. kmalloc vs vmalloc (必考)

| 特性 | kmalloc | vmalloc |
| :--- | :--- | :--- |
| **實體連續及** | 是 (Physically Contiguous) | 否 (Virtually Contiguous) |
| **分配區域** | Direct Mapping (Low Mem) | vmalloc area (High Mem) |
| **效能** | 快 (無 Page Table 修改) | 慢 (需建立 Page Table + TLB Flush) |
| **DMA** | **可以直接用** | **不能直接用** |
| **用途** | 一般 Kernel 物件、DMA Buffer | 載入 Module、超大 Buffer |

## 🔷 Logic IV: 穩定性與並發

### 1. OOM Killer (Out of Memory)

當 RAM 耗盡且無法 Swap/Reclaim 時，Kernel 會啟動殺手。
-   **Score**: `oom_badness()` 計算誰最該死 (佔用多、非 root)。
-   **Protection**: `echo -1000 > /proc/<pid>/oom_score_adj` 可保命。

### 2. Memory Barriers (記憶體屏障)

為了效能，Compiler 和 CPU 會**重排指令順序 (Out-of-Order Execution)**。在多核心溝通時這會導致災難。

-   **Data Dependency**: 單核心內，CPU 保證結果正確。
-   **SMP**: CPU A 寫 `data=1; ready=1;`，CPU B 可能先看到 `ready=1` 卻讀到舊的 `data`。
-   **解法**:
    -   `smp_wmb()`: 確保寫入順序 (Write Barrier)。
    -   `smp_rmb()`: 確保讀取順序 (Read Barrier)。
    -   `mb()`: 確保讀寫都不越過屏障 (Full Barrier)。

## 📝 精選面試題 (Interview Questions)

### Q1: 什麼是 TLB Miss？如何減少它？
-   **TLB Miss**: CPU 在 TLB 找不到 VA 對應的 PA，需由 Page Table Walker 遍歷記憶體中的 Page Table (慢)。
-   **減少方法**:
    1.  **Huge Pages**: 使用 2MB 或 1GB Page，一個 TLB Entry 覆蓋更大範圍。
    2.  **Locality**: 程式資料結構盡量緊湊，增加空間局部性。
    3.  **ASID**: 避免 Context Switch 時 Flush TLB。

### Q2: 為什麼 `malloc` 分配記憶體後，系統的 Free Memory 沒有立刻減少？
-   因為 Linux 採用 **Demand Paging**。
-   `malloc` 只是由 glibc 在 User Space 標記區塊，或透過 `brk`/`mmap` 向 Kernel 申請 VMA (地址範圍)。
-   實體 Page 是在**第一次寫入**觸發 Page Fault 時才真正分配的。

### Q3: 請比較 `kmalloc`, `vmalloc`, `malloc`。
-   `malloc`: C Library 函數，User Space 使用。
-   `kmalloc`: Kernel Space 使用，分配**實體連續**記憶體，適合 DMA，底層是 Slab/Buddy。
-   `vmalloc`: Kernel Space 使用，分配**虛擬連續**但實體不連續的記憶體，適合軟體用的大 Buffer，不適合 DMA。

### Q4: OOM Killer 如何選擇要殺掉的 Process？
-   計算 **OOM Score** (基於 RSS 記憶體使用量)。
-   加上 `oom_score_adj` (User 可設定的權重)。
-   優先殺掉：非特權 (User)、佔用大量 RAM 的 Process。
-   保護：`init` process (PID 1) 和 Kernel Threads 免疫。

### Q5: 為什麼 ARM 架構比 x86 更需要 Memory Barrier？
-   **x86**: 採用 **TSO (Total Store Ordering)** 模型，硬體保證大部分的讀寫順序，只有 Store-Load 需要 Barrier。
-   **ARM**: 採用 **Weakly Ordered** 模型，硬體允許 Load-Load, Store-Store 等各種重排來提升功耗比。因此在驅動開發或 Lock-free 編程時，必須顯式使用 `dmb` / `dsb` (或 Kernel 的 `smp_mb` 巨集)。
